# saml2-sp

Java service provider for SAML 2.0 Web Browser SSO, plus a Shared Signals poll receiver and an embedded iya-sts PEP. MIT. This work stays on `develop` until `com.iyasec:iya-pep:0.1.0` is on Maven Central: a merge to `main` publishes the library, and that publish cannot depend on a git pin. `develop` is ahead of `origin/main`. A pull request merged into `main` publishes the library (`library/` only; the demo never) to Maven Central after the test workflow succeeds on that commit. A direct push does not. `publish.yml` runs `mvn -Prelease -f library/pom.xml deploy` in the Maven container: the `release` profile adds the sources and javadoc jars, a GPG signature on every file, and the Central publishing plugin, which uploads, publishes and waits until the release is live. Maven Central has no trusted publishing, so the job uses four repository secrets: `CENTRAL_TOKEN_USERNAME` and `CENTRAL_TOKEN_PASSWORD` (a Central Portal user token) and `GPG_PRIVATE_KEY` and `GPG_PASSPHRASE` (the release signing key, whose public half is on a public key server). A release happens when the library's files changed since the last release's tag: `publish.yml` takes one patch above the highest published version, publishes it, and creates the matching tag and GitHub Release. A change to tests, the demo, or the docs releases nothing. To choose a version or start a new minor, raise `VERSION`; the version is stamped in CI and is not committed, so the manifests can trail what is published. `-Dcentral.skipPublishing=true` builds and signs everything and uploads nothing.

## Usage

`ServiceProvider.fromFile("saml.json")`, then `login` and `acs(method, url, body, requestId)`. JSON keys match the Node configuration (`entityId`, `acsUrl`, `privateKey`, `certificate`, `idpMetadata`, bindings, `signals`, `ssf`). Methods match the TypeScript names (`fromFile`, `login`, `acs`, `postFormHtml`). Group `com.iyasec`, artifact `saml2-sp`, packages under `com.iyasec.saml`.

`signals` omitted or `true` keeps the receiver available and is omitted from the resolved configuration. `false` does not start a receiver and does not require transmitter metadata, and the resolved configuration includes `signals: false`. A non-boolean raises `signals must be true or false`. The flag does not change the AuthnRequest: SAML does not send OAuth scopes.

Request bindings are `redirect` and `post`. Response bindings are `post`, `redirect`, and `artifact`. Artifact resolution is a signed SOAP `ArtifactResolve`. HTTP-Redirect query signatures use RSA-SHA256 (`http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`). Success is `urn:oasis:names:tc:SAML:2.0:status:Success`. `com.iyasec.saml.Cli generate-keys` writes a self-signed RSA certificate.

## Errors

`Caught.error` records a caught exception through `java.lang.System.Logger`, including the stack, and the method then throws the `SamlError` it already threw. The caught exception is the cause. `Caught.warn` is the same record when the method recovers and does not throw: a later signing key, a poll retry, a false verification, sign-out cleanup, or a handler that must still acknowledge the Security Event Token. A `catch (SamlError)` that only throws that error again is not logged a second time.

## Tests

```bash
docker build --target test .
```

The `test` stage runs `mvn -B test` in `maven:3.9-eclipse-temurin-26`, with `git`, `ca-certificates`, `python3` and `openssl`. Before the suite it clones `https://github.com/rcbj/iya-pep-java.git` branch `develop` and runs `mvn -B -f /opt/iya-pep/pom.xml -DskipTests install`. One clone; a missing `develop` is not retried. The build stage does the same install before `mvn -B -DskipTests package`, or the demo image cannot compile. `TrustChainTest` uses `python3` and `openssl` (the install script's code and `scripts/trust_chain.py` write the four-certificate chain to `idpCa`'s path; the library trusts the provider and a reissued leaf through that file, and refuses a forged leaf followed by the real CA certificates and the right chain under the wrong host name). GitHub Actions uses `docker build --target test`. Do not run Maven or javac on the host. Signatures and decryption are real (JDK ciphers, Apache Santuario exclusive canonicalization). Nimbus JOSE verifies Shared Signals JWS only. The stub identity provider is `library/src/test-fixtures/java/com/iyasec/saml/StubIdp.java`. The stub tests do not start iya-sts. Bytecode is 17 (`maven.compiler.release` 17). The test image is `maven:3.9-eclipse-temurin-26`. The demo runtime image stays `eclipse-temurin:25-jre`.

`python3 scripts/live_iya_sts.py` signs the demo in to iya-sts and checks credential-change and session-revoked on `GET /live-status`. It builds the demo the way a user does: in a scratch copy of the checkout, the install script first (writing the key pair, the metadata and the `idpCa` chain; its Java CLI runs in the demo image), then the image build, then the run with only `sp.key`, `sp.crt` and `idp-metadata.xml` mounted. No CA mount, no `idpCa` rewrite; it checks the image holds the chain and no key. Secrets go to docker as `-e NAME`; no log line carries a sign-in URL. The nightly workflow runs the unit suite and that script once every 24 hours. Neither binds port 3000, 8081 or 18481-18495; the defaults are 18555 and 18655. Push CI stays the unit suite.

`idpCa` (`file:generated/idp-ca.pem`) is the iya-sts TLS listener CA trust chain. `scripts/configure_iya_sts.py` writes the whole chain there on every run through `scripts/trust_chain.py` (`GET /tls/server-certificate`, falling back to the handshake). `Backchannel` makes every block a PKIX trust anchor (a presented leaf counts only if it is itself in the file; otherwise the chain must verify to an anchor), and `HttpClient` still verifies the host name. The demo image bakes the file in (`COPY demo demo` after the compile; `.dockerignore` admits only that file of `demo/generated`, so keys and metadata never enter an image, and a build without it succeeds). Rebuild the image after re-running the install script against a different iya-sts. Do not replace the directory COPY with one that names the file or globs for it: both builders fail when it is absent. A generated test-user password goes to `demo/generated/<user>.password` (mode 0600), never to the output.

**Plain http (#17).** `Backchannel.send` is the one place every fetch goes through (metadata URL, `ArtifactResolve`, SSF configuration, JWKS, stream and poll). `refusePlainHttpOffLoopback` refuses plain `http://` to a host that is not loopback (`127.0.0.0/8`, `::1`, `localhost`) before connecting, without resolving a name, naming only the scheme and host[:port]; userinfo is never loopback. Redirects are followed by hand (`Redirect.NEVER`, at most five hops, the JDK's method rules, never https to http) so each hop gets the same check. A URL or `Location` holding whitespace or a control character is refused first (`refuseWhitespaceOrControl`), so no two parsers can disagree about the host. No opt-out. `PlainHttpTest` covers it; `http://0.0.0.0:<port>` reaches a 127.0.0.1 listener on Linux, so an empty backlog proves no connection was opened.

## Embedded PEP

The PEP is `com.iyasec:iya-pep` 0.1.0. This library wires it in `com.iyasec.saml.pep.SamlPep`. A `pep` section is off unless present. There is no feature flag: the dependency is always on the classpath. A missing `mode` is `local`.

`ServiceProvider.create` and `fromFile` build and start it after `refreshMetadata`. `pdpUrl` defaults to the identity provider's entityID (iya-sts's realm issuer). `application` defaults to `entityId`. `tlsCa` defaults to the `idpCa` PEM. `signals` defaults to whether the receiver runs (an `ssf` object, and `signals` not `false`). A relative `assertionKey` is joined to the configuration directory; the PEP reads the file itself.

`SamlPep.build` refuses a PEP key whose JWK thumbprint equals `privateKey` or `ssf.clientKey`. `SignalsReceiver.start` refuses again when the TLS client key it will use (`ssf.clientKey`, else the SP `privateKey`) matches `pep.keyThumbprint()`.

The subject id is `SamlLogin.username()`: `username`, else `preferred_username`, else `urn:oid:0.9.2342.19200300.100.1.1`, else `uid`, else `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name`, else the NameID. `SamlPep.subjectOf` puts every attribute (and FriendlyName, when it is not also a Name) on the subject, plus `acr` from `AuthnContextClassRef`, `amr` from `amr` or the AD FS authnmethodsreferences claim, and `auth_time` as epoch seconds from `AuthnInstant`.

`decide(SamlLogin, Access)` asks the PEP. With no `pep` section it is Unavailable, `no pep section is configured`. `decideSession(MemorySessionIndex, localId, login, access)` is a Deny, `no signed-in session`, when the index does not hold that id or the session has expired, and it does not ask the engine. `Decision.httpStatus()` is 200 only for a Permit, otherwise 403.

`SignalsReceiver.pep(Pep)` asks for `Pep.POLICIES_CHANGED_EVENT` when the mode is `local` or `permitCacheMs` is greater than 0 (`SamlPep.wantsEvents`). A reused stream is PATCHed with the types it lacks; a refusal is logged and the receiver still starts. The stream state is `requested` or `excluded` at start and after a good poll, and `down` after a failed poll and on `stop()`. A verified event body goes to `onPolicyEvent`. Add Subject (`iss_sub` and `email`) is queued on `track`; Remove Subject is queued from `untrack` and from an ending event (`forget` / `MemorySessionIndex.take`) when that identifier has no session left. The application's opaque subject `{format: opaque, id: application}` is added at start and never removed. `ssf.addSubjects` defaults to true. Without the transmitter's add and remove endpoints, nothing is sent. A 403 is a warning, stored on `subjectError()`, and not retried.

`ssf.clientCertificate` and `ssf.clientKey` are both or neither (PEM or a path). The demo presents that pair for mutual TLS, else the SP key pair, plus `idpCa`.

The demo's `GET /attribute-protected` (`read` / `attribute-protected` / `attr1`) and `/orders/<id>` (`read` on GET, `write` otherwise, type `order`) use `decideSession` and `httpStatus()`. Signed out is 401. A Deny, an Unavailable decision, or a service provider that will not load is 403. `GET /live-status` includes `pep` (from `status()`) when the file has a `pep` section. `GET /pep-status` is that status as JSON and needs a sign-in. The three-tab pane UI, `pep.js`, the AuthZEN case table and the Playwright live UI are not in this library.

`scripts/configure_iya_sts.py --pep` (`local` when the mode is left out, `--pep-name` default `pep-saml-demo`) creates the `remote-peps` account, a P-256 key at `generated/pep-key.pem` (0600, never printed), `issue-pep-credential` or `set-pep-application`, the catalogue row `subject.acr` → `urn:example:acr`, the application's own policy (never the realm root), and `attr1=abc123` on the test user. It writes the `pep` section and keeps other members. With an `ssf` block it issues the receiver's own TLS client certificate (`issue-tls-client-certificate`) into `generated/ssf-client.key` (0600) and `ssf-client.crt`, and retires an earlier SP trust anchor. It does not add the SP certificate to the process-wide truststore. No secret is printed.

## Layout

Two Maven modules under an aggregator `pom.xml`, which builds both and is never published; keep its version, the library's and the demo's equal to `VERSION`. `library/` is `com.iyasec:saml2-sp`, the library alone: its `pom.xml` inherits nothing, so it is complete as published, and its jar carries no demo class. `library/src/main/java/com/iyasec/saml/` library, `ssf/` receiver, `library/src/test/java/`; `library/src/test-fixtures/java/com/iyasec/saml/StubIdp.java` is the stub identity provider, which both modules' tests compile (build-helper) and no published jar carries. `demo/` is `com.iyasec:saml2-sp-demo`, never published: `com.iyasec.saml.demo.Demo`, and `TrustChainTest` (run from the repository root); its jar and `target/dependency` (the library among them) are what the image runs as `saml2-sp.jar:dependency/*`. Then `scripts/configure_iya_sts.py`, `scripts/live_iya_sts.py`, `Dockerfile`, `docker-compose.yml`, `.github/workflows/nightly.yml`. The image name is `saml2-sp-java-demo`. Compose uses `network_mode: host`, service `saml-demo`, and `ENV PORT=3000` in the image. The health check is `http://127.0.0.1:${PORT}/healthz`. The live script never binds port 3000 or 8081.

## Demo

`docker compose up --build`. `GET /healthz` is `200` with body `ok` and does not load the service provider. Pages: sign-in, `/login` (redirect or POST form), `/saml/acs`, logout of one account or every account, metadata, per-account Shared Signals events, `/attribute-protected` and `/orders/<id>`. `GET /live-status` does not need an account id. It is JSON: `signedIn` is true when any local account session exists, plus `subject` (the username, else the NameID), the receiver state, and accepted events (`type` and `jti` only). With a `pep` section it also has `pep`. No tokens. Loopback entityID and assertion-consumer URLs follow `PORT`. Other hosts stay as written. `PUBLIC_URL` or `--public-url` replaces the origin and keeps the path. The default `http://localhost:3000` is not an explicit public URL. `demo/saml.json` uses `file:` placeholders and omits `signals`. Do not commit `demo/generated/`. The live script and the nightly workflow never bind port 3000 or 8081.

## Signals

With an `ssf` block and without `"signals": false`, the demo starts one poll receiver. Mutual TLS uses `ssf.clientCertificate` and `ssf.clientKey` when both are set, otherwise the service provider's certificate and key, plus `idpCa`. The first poll runs on a background thread so a down transmitter does not block a page. The receiver and the demo share one `MemorySessionIndex`. `scripts/configure_iya_sts.py` registers the SP metadata, pins AES-256-GCM / RSA-OAEP, turns on multiple accounts, and, unless signals are off, grants `ssf.manage` and has the realm issue the receiver's TLS client certificate. It does not put the SP certificate in the process-wide truststore. The container `PORT` wins over the shell `PORT` at registration. The assertion SessionIndex is not the CAEP session id. On `session-revoked`, the event handler ends this demo's one session and says so. `session-revoked` leaves `signedIn` false.
